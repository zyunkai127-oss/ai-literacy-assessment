## 0. 一页结论

队友的方向是**让过程更自然**：去掉预写的错误说法和组员消息，换成一个能看到全部资料的真实模型自由对话；提交后直接出结果；结果页给出总分百分比和逐项得分。工程质量明显提升。

问题在于：**新会话里没有任何受控的错误说法，Critical 永远是 Insufficient Evidence**。剩下能测的只有指令写得具体不具体、作业是否达标、照搬程度、隐私、注明来源。按 02 的节点审查，这些大多是一般学术能力，不依赖 AI。也就是说，产品会失去 brief 最核心的那一项（critically），评委试玩时也看不到"自信地错"这一幕。

**推荐的合并方式："自然的工作流 + 少量受控时刻"**：

- 交互外壳、工程改进、透明的逐项规则展示，用队友的。
- 测量内核用 v2：预写的研究摘要（含错误说法和诱饵）、AI 坚持、代写邀请、一屏汇报、判断类型和 Beta 分档。
- 两边已经一致的原则直接保留：没有证据就不计分；打开资料不等于核实过。

需要团队拍板的有 9 项，见第 3 节。每项都附了推荐。其中 D1（是否保留受控说法）和 D4（是否出总分）最关键。

## 1. 队友改了什么

### 1.1 考生体验

| 环节 | 原版（`main`） | 队友版 |
|---|---|---|
| 开始页 | 任务说明加开始按钮 | 分成 Project Introduction / Requirements / Expected Deliverables / Additional Resources 四块；**开始前就能浏览资料包** |
| 工作区左栏 | 资料包，四个可折叠部分 | "Project references"：项目要求和嵌套的资料包，都默认收起 |
| AI 对话 | 第一条消息返回预写草稿（带 Insert 按钮），追问说法时 AI 坚持，其余问题交给模型 | **全部交给真实模型**；模型能看到任务和完整资料包（姓名已脱敏）；没有草稿，也没有 Insert 按钮 |
| 无 API key 时 | 预写回复兜底，可以完整演示 | 对话不可用，只能看资料、写简报 |
| 组员消息 | 完整版 60 秒后出现 | 删除 |
| 写简报 | 文本框加字数 | 加上 "80–150 required" 提示和最大长度限制；提交前等所有待保存的事件写完 |
| 汇报环节 | 三个问题 | **删除**，提交后直接出结果 |
| 结果页 | 开头一条、逐张翻牌、四个维度档位、三条建议 | **总分百分比**、四个维度百分比、逐项"得分 / 失分"（附评分规则和证据）、个性化反馈 |
| 知情同意文案 | "不出总分，不排名" | 删掉了这句；说明聊天内容（已脱敏）会发给 AI 提供方 |

### 1.2 评分

- 每项仍是 0/1/2，但**没有证据的项记为 null，不计入分母**。
- 总分和维度分 = 得分 ÷ 可得分，四舍五入成百分比。
- 打开资料"只记录访问，不能单独证明核实过"。
- 新增：在聊天里明确说某条说法是错的（不是提问，也不是引述别人），算作明确的拒绝。
- 新增：如果草稿快照里曾经有错误内容，最终版里删掉了，算作"有记录的修改"，给 1 分（打开过对应资料给 2 分）。
- 新增：按资料包的 10 个事实识别成品里的数据点，要求每个数据点在**同一句**里注明来源。
- 新增：照搬程度对比的是**全部 AI 回复**，不只是草稿。
- 新增：第一条指令跳过寒暄（"hi""你好"）；只有同意存储时才在反馈里引用原文。
- 兼容旧会话：数据库里旧规则下的结果照原样显示。

### 1.3 Guardrail

- 姓名脱敏改为不区分大小写，并且对历史消息和资料包也做脱敏。
- 套取答案、要求代写**只记录，不再改变助手的行为**：不再返回固定的拒绝，也不再切换成只引导的模式。
- 代写识别的正则更严格，误报更少。

### 1.4 工程

- 同一会话同时只允许一条回复在生成，避免并发写入。
- 模型调用设了 30 秒超时、不自动重试，并把 401、404、429 等错误翻译成学生看得懂的提示。
- 结果保存和清除未同意存储的数据放在同一个数据库事务里。
- 新增 `chat.test.ts`，覆盖系统提示的内容、空密钥、模型报错。
- `/ops` 增加了失败回复的计数。

### D1　受控说法：去掉，还是保留（核心）

**队友的考虑**（从改动推断）：预写的草稿和定时出现的组员消息显得刻意；真实模型自由对话更像学生平时用 AI 的样子，也更符合 Reply 对实时流式 AI 的要求。这和组内之前"想测自然状态"的顾虑一致。

**去掉的代价**：

1. Critical 在每个新会话里都是 Insufficient Evidence，评委试玩时这一格永远是空的。
2. 模型能看到全部资料，又被要求"纠正之前的错误"，几乎不会出错。没有错误可以识别，就测不到"该怀疑的时候怀疑"。
3. 剩下的节点里，注明来源、是否达标测的是一般学术能力，不依赖 AI。这正是此前"测的是不是别的能力"那条质疑。
4. Reply 的官方示例里已经有"找出 AI 答案中的错误"；完全去掉之后，原创性只能靠一个普通的写作打分器来撑。

**推荐：混合模式**。自然和受控不必二选一：

- 学生的第一条**任务指令**（跳过寒暄，沿用队友的寒暄识别）触发一份"研究摘要"。摘要是预写原文，逐条列出说法，每条带 Insert 按钮。对学生来说，这就是"让 AI 先查一下资料"，很自然。
- 之后的对话：追问某条具体说法时，AI 按剧本坚持；其他问题全部交给真实模型，用队友的新系统提示和错误处理。
- 这样评委看到的是一个真实、能流式回复的助手，同时每个考生都面对同样的 3 条错误说法和 2 条诱饵。

### D2　真实模型能否看到三份证据资料的正文

**队友的做法**：系统提示里放入完整资料包，让模型的回答有依据、不乱编。

**冲突**：如果模型能看到原始数据，学生只要问一句"每周用 AI 的比例是多少？"，模型就会答 56%，和摘要里的 65% 直接矛盾。这样，核实预算形同虚设（问 AI 是免费的核实渠道），"AI 坚持后是否屈服"也测不到了。

**推荐（方案 A）**：模型只拿到任务说明、学生留言（已脱敏）和它自己写过的研究摘要。系统提示要求：不引入摘要和学生粘贴内容之外的新数字或文献；学生要求核实某条说法时，建议去看资料包。保留队友提示里"不编造引用""学生留言保持匿名"等内容；删掉"纠正之前的错误"这一句。

**方案 B（如果团队更看重模型有依据）**：照队友的做法给全部资料；取消核实预算；把"问 AI 后改正"也算作有针对性地行动。代价是辨别这一项会变得很容易，Decide 里"AI 坚持后是否屈服"这一项也基本测不到。

### D3　汇报环节

**队友的考虑**：少一步，评委版更快，提交即看结果。

**冲突**：v2 的 Discern 和 Decide 都要用到"标记不采信"和"最没把握的地方"；Own 要用到使用声明。

**推荐：压缩成一屏**，提交简报后弹出：

| 区块 | 形式 |
|---|---|
| 助手的每条说法 | 每行三个选项：Relied on it / Not sure / Didn't rely on it。"Didn't rely" 就是标记不采信；"Not sure" 就是最没把握，最多选 2 条 |
| 整体把握程度 | 滑块 |
| 措辞主要是谁写的 | 三选一 |

评委版大约 20 秒。追问只在完整版出现，因为它要用到上面的回答来选题，需要单独一步。

另外采纳队友的一个好点子：**在聊天里明确说某条说法是错的，也算作标记不采信**。这是工作过程中自然留下的判断，学生不必等到汇报时再表态。

### D4　总分百分比

**队友的考虑**：一个醒目的数字，评委一眼能看懂，也便于做群体对比。

**不出总分的理由**：

1. 把节点加起来需要权重，而权重目前没有任何依据。百分比只是在掩盖这一点。
2. 每个人可得的分数不同（证据不足的项不计入）。两个人都是 75%，背后的项目可能完全不同，彼此不可比。队友在 README 里自己也写了这一条局限。
3. 产品文档、v1.0、v2 和原版知情同意页都承诺过"不出总分、不排名"。一旦有了总分，学生和老师就会去刷分（Goodhart 定律），形成性评估的定位也就站不住了。

**推荐**：不出总分。保留队友的透明展示：每一项写出评分规则和本次的证据。如果团队坚持要一个醒目的数字，可以用计数代替百分比，比如 "You handled 4 of 6 key moments well"，并注明不同会话之间不可比。

### D5　Guardrail 只记录，还是改变行为

**推荐：改变行为**。03 引用的 Reply Track A 要求里明确写着"随用户状态调整行为的 guardrail（含防提示注入）"。只记录不改变，等于放弃了这一项评分点。

做法：要求代写后助手切换为只引导；套取答案或系统提示时返回固定拒绝，不交给模型。同时采纳队友改进后的代写识别正则（误报更少），以及不区分大小写的姓名脱敏。

### D6　草稿里出现过错误、最终删掉了

**队友的做法**：算作有记录的修改，给 1 分（打开过对应资料给 2 分）。

**推荐：不计分，只在复盘里展示**。理由是删减可能只是为了把字数压进 150 词，未必代表判断；而且正确的说法被删掉时，按对称原则也得算误报，会误伤只是在缩短篇幅的学生。学生如果明确表态（在聊天里说错了、汇报时标记了），自然会被计入。

### D7　开始前能否浏览资料包

**推荐：不能**。开始页沿用队友的四块结构，但去掉资料包。否则学生可以在计时开始前读完全部资料，核实预算和时间压力都会失效。

### D8　没有 API key 时

**推荐：合并两边**。研究摘要和 AI 坚持都是预写的，不需要 key，所以核心测量离线也能完整运行；只有自由对话显示队友写的 "Live AI chat is unavailable"。现场网络或额度出问题时，评委仍然可以完整玩一局。

### D9　旧会话的兼容代码

**推荐：不保留**。目前数据库里只有开发时的测试数据，清空即可。去掉兼容分支能让评分和结果页的代码简单很多。

1. **先把队友的版本放进 git**（5 分钟）。队友把本地文件夹提交到 `feature/phase1-live-chat` 并推送。`.env.local`、`data/app.db`、`tsconfig.tsbuildinfo` 都已被 `.gitignore` 排除，不会被误提交。如果队友不方便，可以由我从你上传的这份副本代为提交。
2. **团队确认 D1–D9**（15 分钟），重点是 D1 和 D4。
3. **从 `feature/phase1-live-chat` 拉出 `feature/merge-v2`**，按以下顺序改：
   1. `types.ts` 和 `scenario.json`：v2 的字段，加上队友新增的字段。
   2. `scoring.ts`：按 01 实现，并吸收 4.2 的五项改进。五位考生的测试先跑通。
   3. 路由：`chat` 的混合路由、一屏汇报、完整版追问。
   4. 界面：保留队友的外壳，加上预算、Insert 按钮、一屏汇报、v2 结果页。
4. **时间不够时的取舍**：
   - **P0**：D1 混合模式、一屏汇报、v2 评分、结果页画像。
   - **P1**：核实预算、代写邀请、主动 guardrail。
   - **P2**：完整版追问、第二意见 AI。
